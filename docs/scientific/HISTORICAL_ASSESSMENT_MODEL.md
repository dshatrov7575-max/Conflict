# Historical Assessment Model — Conflict Analysis MVP7

Версия описания: `0.1.0`. Версия JSON Schema: `1.0.0`, Draft 2020-12.
Статус исследовательской процедуры: `PROPOSAL`. База PR-7:
`b0a1fc97ad6ffc1c275f7c27a6a2c9bda47c142a`.

## Назначение

Historical Assessment — структура для будущей ручной исследовательской
интерпретации наблюдаемых признаков. Она сохраняет связь интерпретации
с Evidence и Factor Mapping, неопределённость и разногласия, чтобы позднее
выполнить отдельное сопоставление с историческим исходом по
[Validation Protocol](VALIDATION_PROTOCOL.md).

```text
Evidence
    ↓
Observed Indicator
    ↓
Factor Mapping
    ↓
Historical Assessment
    ↓
Validation Record
```

Стрелки обозначают происхождение и порядок работы, а не причинность или
автоматическое получение результата. Эта поставка создаёт контракт и пустой
шаблон; HUMAN coding, factor scoring и validation conclusion не выполняются.

Слой существует только в `docs/scientific`. Приложение его не загружает.
Calculation Core, `POLARIZATION_V1_BETA`, веса, Factor Ontology, Scenario
Modeling и Evidence datasets не меняются. Здесь нет адаптера в ParameterValue,
BetaWeights, snapshot или CalculationRun, расчёта UNO, итоговых баллов,
оценки страны или прогнозирования.

## Evidence ≠ Assessment

| Уровень | Содержание | Граница утверждения |
| --- | --- | --- |
| FACT / Evidence | Что подтверждено указанными источниками, с сохранением конкретного сообщения, происхождения и ограничений. | Наличие публикации подтверждает факт сообщения; истинность сообщаемого требует проверки. Противоречия не удаляются. |
| INDICATOR | Какой наблюдаемый признак выделен из Evidence и связан с фактором. | Формулировка признака не является баллом или доказательством причинности. |
| Factor Mapping | Проверяемая связь признака с существующим `factor_id`. | Принадлежность к категории не определяет силу фактора или исход. |
| ASSESSMENT | Исследовательская интерпретация в явно указанных границах, с Evidence-ссылками и rationale. | Интерпретация не переписывает факт и не становится числовым входом Core. |
| VALIDATION | Отдельное сопоставление зафиксированной оценки с независимо описанным историческим исходом. | Сопоставление требует зарегистрированного протокола; заполнение assessment не означает валидацию модели. |

Обязательные правила:

- Неизвестное остаётся `UNKNOWN`, соответствующее значение — `null`.
- Спорное остаётся `DISPUTED`; альтернативы и противоречащие Evidence
  сохраняются в rationale, без выбора удобной версии или усреднения.
- Отсутствие данных не является отсутствием фактора. `[]` и `null` не
  преобразуются в ноль, «нет влияния», «нет конфликта» или нейтральность.
- Каждая интерпретация и каждый заполненный индикатор должны иметь
  `evidence_references` и rationale. Rationale указывает, какое свидетельство
  поддерживает или оспаривает какую часть утверждения.
- `status` и `confidence` не копируются из Evidence, Mapping или онтологии
  автоматически; их обоснование относится к конкретной интерпретации.
- Известный исход не используется для выбора признаков, акторов, PTN,
  границ эпизода или рубрик. Правила применяются вместе с
  [NON_INFERENCE_RULES.md](NON_INFERENCE_RULES.md).

## Контракт HistoricalAssessment

[HISTORICAL_ASSESSMENT_SCHEMA.json](HISTORICAL_ASSESSMENT_SCHEMA.json) описывает
документ с `schema_version`, `document_kind` и непустым массивом `assessments`.
`document_kind=STRUCTURE_ONLY` означает пустой шаблон;
`HISTORICAL_ASSESSMENT` — будущий рабочий документ, а не научный статус.
Тип отдельной записи доступен как `$defs.HistoricalAssessment`.

Все поля обязательны. Отсутствие значения записывается явно; схема не
присваивает значения по умолчанию. Дополнительные поля запрещены.

| Поле | Смысл и форма |
| --- | --- |
| `assessment_id` | Уникальный ID будущей записи в документе; `null` в структурном шаблоне. |
| `case_id` | Существующий ID кейса в связанном Case Mapping. |
| `factor_id` | `POS`, `KVS`, `RGU`, `KVPTN` из [каталога](factors.metadata.json), либо `null`, пока фактор неизвестен. Новые факторы не вводятся. |
| `evidence_references` | Массив существующих `evidence_id` того же кейса и эпизода, перечисленных в `evidence_reference` выбранного Mapping. `[]` — свидетельства пока не выбраны. |
| `observed_indicator` | Наблюдаемый признак как текст либо `null`. Не число и не степень влияния. |
| `assessment_value` | Качественная исследовательская интерпретация как текст либо `null`. Числовые баллы, веса, ранги, проценты и числа, замаскированные строками, запрещены. |
| `confidence` | `UNKNOWN`, `LOW`, `MEDIUM`, `HIGH`: качественная уверенность именно в интерпретации; не вероятность события и не ранг фактора. |
| `rationale` | Обоснование связи с каждым используемым Evidence, области применимости, уверенности, ограничений и разногласий; либо `null`. |
| `assessor_type` | `HUMAN` только для действительно выполненной ручной интерпретации; `null`, пока оценщик не зафиксирован. Этот контракт не создаёт AI-оценок. |
| `status` | `CONFIRMED`, `PARTIAL`, `DISPUTED`, `UNKNOWN` в пределах определения ниже. |

Служебное поле `factor_mapping_reference` связывает каждую запись с конкретным
Mapping: `reference` (путь от корня репозитория, URI или устойчивый указатель),
`sha256` (хеш байтов документа), `json_pointer` (указатель на объект Mapping),
`mapping_id` (его существующий ID). Поле может быть `null`, пока связь не
установлена; оно обязательно заполнено при наличии Evidence или интерпретации.
Хеш фиксирует версию, но не доказывает истинность и временную допустимость.

Evidence разрешаются через закреплённый Mapping-документ и его
`source_reference` по [Case Mapping Model](CASE_MAPPING_MODEL.md). Пустой
Mapping не заменяет Evidence; ID Mapping нельзя использовать как evidence_id.
Разные интерпретации одного фактора допустимы в отдельных записях с разными
assessment_id. Они не объединяются автоматически и не создают числовых вкладов.

### Статусы

| Статус | Значение |
| --- | --- |
| `CONFIRMED` | Интерпретация обоснована указанными свидетельствами в заявленных границах. Не подтверждает причинность, валидность модели или расчётный вход. |
| `PARTIAL` | Поддержана только часть интерпретации; пробелы перечислены в rationale. |
| `DISPUTED` | Есть несовместимые интерпретации или свидетельства; assessment_value описывает предмет разногласия, rationale сохраняет альтернативы. |
| `UNKNOWN` | Интерпретация не установлена; assessment_value остаётся null, confidence — UNKNOWN. Известные Evidence и индикатор можно сохранить с обоснованием. |

Для трёх непустых статусов нужны assessment_id, известный factor_id,
закреплённый Mapping, Evidence, индикатор, качественная интерпретация,
rationale и `assessor_type=HUMAN`. Уверенность может остаться `UNKNOWN`:
`CONFIRMED` не назначает автоматически `HIGH`. Схема проверяет наличие
обоснования, но не его качество и не правомерность выбранного статуса.

## Граница с Validation Record

Будущая работа до интерпретации должна закрепить методику и её версию,
единицу анализа (актор/PTN, время, эксперимент в применимой области),
границы эпизода, окно исхода, information cutoff и допустимые версии Evidence.
Эта область указывается в rationale и связанных материалах протокола;
текущая минимальная схема сама по себе не является полной кодировочной рубрикой.
В онтологии подтверждённый универсальный набор индикаторов пока отсутствует;
его нельзя объявить установленным заполнением свободного текста.

Правила cutoff и независимого описания исхода остаются в
[Validation Protocol](VALIDATION_PROTOCOL.md) и
[Empirical Validation Pilot](EMPIRICAL_VALIDATION_PILOT.md). Если доступность
версии источника до cutoff неизвестна, она не допускается как pre-event input.
Поздние материалы об исходе не возвращаются в assessment.

Готовый документ в будущем может быть закреплён через
`ValidationPilot.historical_assessment_reference` вместе с хешем и указателем
на запись. [ValidationRecord](VALIDATION_SCHEMA.json) остаётся отдельным
контрактом: связь с assessment фиксируется в плане/отчёте по его существующим
полям, без добавления нового поля в прежнюю схему. Ни шаблон, ни качественная
интерпретация не заменяют требуемые ей snapshot и CalculationRun.
Никакая ValidationRecord или conclusion этой поставкой не создаётся.

## Шаблон Жанаозена

[ZHANAOZEN_2011_ASSESSMENT_TEMPLATE.json](ZHANAOZEN_2011_ASSESSMENT_TEMPLATE.json)
ссылается на существующий `ZHANAOZEN_2011_EXAMPLE` и четыре
`STRUCTURE_ONLY_POS/KVS/RGU/KVPTN` в
[ZHANAOZEN_2011_EXAMPLE.json](ZHANAOZEN_2011_EXAMPLE.json). Пути, SHA-256 и
JSON Pointer закрепляют именно эти пустые Mapping, а не завершённую разметку.

В исходном примере нет Evidence-записей, поэтому evidence_references остаются
пустыми. assessment_id, observed_indicator, assessment_value, rationale и
assessor_type — `null`; confidence и status — `UNKNOWN`. Наличие четырёх
слотов не утверждает применимость факторов к кейсу. Новые исторические
факты, признаки, выводы, страна, даты или исходы не добавлены.
Существующий шаблон пилота PR-7 не меняется: его
historical_assessment_reference остаётся null, поскольку выполненной оценки нет.

## Технические проверки

JSON Schema проверяется `Draft202012Validator.check_schema`; документы —
валидатором с `FormatChecker`. Синтаксис непустого JSON Pointer дополнительно
ограничен регулярным выражением, поскольку проверка этого format зависит
от опциональных зависимостей jsonschema. `STRUCTURE_ONLY` запрещает
заполнение assessment-полей, Evidence, confidence и статуса. Проверка формы
не является эмпирической валидацией.

Отдельно проверяются SHA-256, разрешимость каждого указателя, совпадение
case_id/factor_id/mapping_id, существование и область Evidence-ссылок,
уникальность непустых assessment_id, локальные Markdown-ссылки и отсутствие
изменений прежних файлов. Истинность, причинность, смысл свободного текста,
доступность источников до cutoff и сохранение всех разногласий требуют
содержательного review; JSON Schema их не доказывает.

Минимальная проверка из корня репозитория:

```powershell
@'
import json
from pathlib import Path
from jsonschema import Draft202012Validator, FormatChecker

root = Path('docs/scientific')
schema = json.loads((root / 'HISTORICAL_ASSESSMENT_SCHEMA.json').read_text(encoding='utf-8'))
template = json.loads((root / 'ZHANAOZEN_2011_ASSESSMENT_TEMPLATE.json').read_text(encoding='utf-8'))
Draft202012Validator.check_schema(schema)
Draft202012Validator(schema, format_checker=FormatChecker()).validate(template)
print('Schema and structure-only template: PASS')
'@ | .\software\conflict_analysis\.venv\Scripts\python.exe -
```

Существующие синтетические Core tests из `software/conflict_analysis`:

```powershell
$env:USE_SQLITE = '1'
$env:PYTHONDONTWRITEBYTECODE = '1'
.\.venv\Scripts\python.exe -m pytest calculation/tests -p no:cacheprovider
```

Это регрессия на отдельной тестовой in-memory SQLite БД; исторический кейс,
рабочая БД и Evidence datasets не используются. После commit граница изменений
проверяется относительно указанной базы PR-7 через `git diff --name-status`:
только четыре добавления этой поставки в `docs/scientific`, без модификаций,
удалений или переименований; `git diff --check` должен завершиться с кодом 0.
