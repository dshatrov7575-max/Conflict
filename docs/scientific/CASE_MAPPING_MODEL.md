# Case Mapping Model — Conflict Analysis MVP7

Версия описания: `0.1.0`. Версия JSON-схемы: `1.0.0`.
Статус проектирования эмпирической операционализации: `PROPOSAL`.
База: PR-4, commit `4cee2e8b7972c1678e6d4b4028f611182eaf7c7d`.

## Назначение Case Mapping

Case Mapping описывает проверяемую связь между свидетельствами исторического
кейса и типами факторов из [Factor Ontology](FACTOR_ONTOLOGY.md). Этот слой
позволяет сохранять происхождение интерпретации, разногласия и неизвестное.
Связь с фактором не задаёт его числового значения и не оценивает конфликт.

```text
Case Dataset
    ↓
Conflict Episode
    ↓
Evidence
    ↓
Observed Factor Mapping
    ↓
Historical Assessment — отдельный будущий этап
    ↓
UNO Replay — будущий этап
```

Текущий результат — самостоятельные документы и JSON-контракт. Приложение
их не загружает. Они не меняют Calculation Core, `POLARIZATION_V1_BETA`,
Scenario Modeling, исторические Evidence datasets, импорт или экспорт.
Существующие источники связываются ссылками; их записи не переписываются.

## Observed Evidence ≠ Model Interpretation

**Observed Evidence** — то, что сообщает конкретный источник, с указанием
версии и места в нём. Поле `observed_evidence` сохраняет содержание сообщения
источника; само наличие сообщения ещё не доказывает его истинность.

**Model Interpretation** — решение исследователя о том, какой наблюдаемый
признак относится к какому фактору и почему. `observed_indicator` является
сформулированным исследователем признаком, а `mapping_rationale` объясняет
связь. Оба поля принадлежат mapping, а не исходному Evidence dataset.
Интерпретация не должна подменять текст свидетельства или устранять
противоречащие источники.

`CONFIRMED` относится к рассмотренной связи, а не к истинности всей истории,
валидности фактора, готовности числовой оценки или наступлению события.
Исход эпизода фиксируется отдельно от mapping и не выводится из факторов.

## Структура документа

[CASE_MAPPING_SCHEMA.json](CASE_MAPPING_SCHEMA.json) использует JSON Schema
Draft 2020-12. Все перечисленные поля обязательны; неизвестное явно
представляется null или пустым массивом. Неизвестное не заменяется нулём,
датой из названия кейса, строкой «нет конфликта» или значением по умолчанию.

Корневой документ содержит `schema_version`, `document_kind`,
`dataset_reference` и массив `cases`. `document_kind` принимает
`STRUCTURE_ONLY` для пустого структурного примера или `CASE_MAPPING` для
заполненного документа связи. Это признак назначения файла, не статус
научной достоверности. `dataset_reference` — ссылка на исходный Case Dataset
либо null, если он пока не выбран.

Ссылка на источник имеет поля `reference` (URI, путь или устойчивый ID),
`version` (версия либо null) и `locator` (страница, строка или иной указатель
либо null). Ссылки не запускают загрузку или импорт. Для воспроизводимого
исследования нужно закрепить конкретную версию источника; null сохраняет
известный пробел, а не разрешает незаметно подставить latest.

### Case

| Поле | Смысл |
| --- | --- |
| `case_id` | Устойчивый ID кейса; название само по себе не является доказательством страны или периода. |
| `country` | Страна как текст либо null; в примере не заполняется. |
| `time_period` | Объект с `start_date` и `end_date`, каждая — точная дата `YYYY-MM-DD` либо null. Известный только год не превращается в вымышленную точную дату. |
| `episode_boundary` | Текстовое правило выделения эпизодов либо null. |
| `source_reference` | Массив ссылок, обосновывающих описание кейса; `[]` означает, что ссылки пока не внесены. |
| `episodes` | Массив эпизодов. `[]` означает отсутствие описанных эпизодов, а не доказанное отсутствие событий. |

### Episode

| Поле | Смысл |
| --- | --- |
| `episode_id` | Уникальный внутри кейса ID эпизода. |
| `start_date`, `end_date` | Границы эпизода: дата либо null; открытая граница не заменяется датой соседнего эпизода. |
| `description` | Описание выделенного эпизода либо null. |
| `outcome_class` | Категория исхода по отдельно обоснованной классификации либо null. В этом PR классификация не устанавливается. |
| `evidence` | Массив ссылочных записей Evidence, доступных для mapping этого эпизода. |
| `factor_mappings` | Массив независимых связей с факторами. |
| `outcome` | Объект Outcome; все его значения могут быть null. |

### Evidence

Каждая ссылочная запись содержит `evidence_id`, `source_reference` и
`observed_evidence`. `evidence_id` уникален внутри эпизода;
`source_reference` — объект ссылки на существующий источник;
`observed_evidence` — сообщение источника либо null, если содержание ещё
не извлечено. Это локальный указатель в mapping-документе, а не новая
историческая запись Foundation Evidence и не замена её ID.

### Factor Mapping

| Поле | Смысл |
| --- | --- |
| `mapping_id` | Уникальный внутри эпизода ID отдельной интерпретации. |
| `factor_id` | `POS`, `KVS`, `RGU`, `KVPTN` из каталога PR-4 либо null, если фактор пока не определён. |
| `evidence_reference` | Массив локальных `evidence_id` того же эпизода; `[]` сохраняет отсутствие выбранных свидетельств. |
| `observed_indicator` | Текст признака, выделенного из свидетельств, либо null; не числовой балл фактора. |
| `confidence_level` | `UNKNOWN`, `LOW`, `MEDIUM`, `HIGH`: качественная уверенность в связи, без процентов и числового ранга. |
| `mapping_status` | Один из четырёх статусов ниже. |
| `mapping_rationale` | Обоснование связи и уверенности, с указанием ограничений и разногласий, либо null. |

Массив `factor_mappings` поддерживает несколько факторов на кейс через его
эпизоды. Один mapping может ссылаться на несколько Evidence из разных
источников. Повтор `factor_id` разрешён: разные признаки, источники и
интерпретации сохраняются отдельными записями со своими статусами и
уверенностью. Это не создаёт дублирующих числовых вкладов или весов.

### MAPPING_STATUS

| Статус | Интерпретация |
| --- | --- |
| `CONFIRMED` | Связь рассмотрена и обоснована указанными свидетельствами в обозначенных границах. Это не статус числового входа Core. |
| `PARTIAL` | Свидетельства поддерживают только часть заявленной связи; недостающее описывается в rationale. |
| `DISPUTED` | Есть несовместимые интерпретации или противоречащие свидетельства; разногласия сохраняются. |
| `UNKNOWN` | Достаточная интерпретация пока отсутствует; уже известные ссылки и признаки можно сохранить без повышения статуса. |

Статус и уверенность — разные оси. Например, `CONFIRMED` не назначает
автоматически `HIGH`; `DISPUTED` не выбирает победивший источник. Схема
не вводит правила усреднения, пороги или автоматические переходы.

Для CONFIRMED/PARTIAL/DISPUTED требуются известный factor_id, непустой признак,
хотя бы одна Evidence-ссылка и rationale. Для известного уровня уверенности
также требуются Evidence-ссылка и rationale. При UNKNOWN разрешены null и
пустые списки. Эти проверки обеспечивают форму обоснования, а не его качество.

### Outcome

| Поле | Смысл |
| --- | --- |
| `event_type` | Текстовая категория события либо null. |
| `escalation_level` | Категория по отдельно определённой методике либо null; числовая шкала и рейтинг здесь не создаются. |
| `resolution_type` | Категория завершения/разрешения либо null. |

Outcome описывается независимо от факторов, по источникам и методике,
указанным в материалах кейса. `outcome_class` и поля Outcome не устанавливают
вероятность или интенсивность конфликта. Неизвестный исход не означает
отсутствие события. Ни одна категория не заполняется в данном PR.

## Границы проверки и будущего использования

JSON Schema проверяет типы, обязательные поля, статусы, неизвестное и форму
ссылок. Проверка дат требует `FormatChecker`. Отдельно проверяются уникальность
case_id, episode_id и mapping_id в своих областях, уникальность evidence_id,
разрешимость Evidence-ссылок внутри эпизода, порядок известных дат и попадание
известных границ эпизода в известный период кейса. Стандартная JSON Schema
не проверяет эти межзаписные отношения или содержание внешних источников.

До научного использования необходимы review границ эпизода и интерпретаций,
проверка источников, независимость кодирования исходов и учёт доступности
свидетельств во времени. Поздние сведения нельзя выдавать за доступные до
события. Недостаток данных сохраняется явно, как требует
[Model Limitations](MODEL_LIMITATIONS.md).

Historical Assessment — следующий самостоятельный этап: ему потребуются
обоснованная рубрика, версия методики, актор/PTN, временной срез и область
эксперимента. Текущий mapping не создаёт ParameterValue, оценок или snapshot.
UNO Replay остаётся будущим этапом; здесь нет его адаптера или запуска.

## ZHANAOZEN_2011_EXAMPLE — только структура

[ZHANAOZEN_2011_EXAMPLE.json](ZHANAOZEN_2011_EXAMPLE.json) содержит имя из задания,
один технический placeholder эпизода и четыре пустых слота известных факторов.
Это не утверждение о числе реальных эпизодов или применимости факторов к кейсу.
Страна, даты, границы, описания, индикаторы и исходы — null; источники и Evidence
отсутствуют; все mapping имеют UNKNOWN. Год не извлекается из ID.

Режим STRUCTURE_ONLY дополнительно запрещает заполнение фактических полей
схемой. Пример не является Case Dataset, Gold Dataset, исторической оценкой
или эмпирической валидацией. Проверки описаны в
[CASE_MAPPING_VALIDATION.md](CASE_MAPPING_VALIDATION.md).
